# ML Testing Assignment: Approach and Explanations

**Senior ML Solutions Architect take-home: fine-tune, optimize, deploy and benchmark a function-calling LLM (ToolACE → BFCL) on 1× H100, targeting Nebius Token Factory.**

Every term is explained the first time it comes up, so this can be used as a briefing for someone new to the topic.

---

## 1. What the assignment is asking, in plain terms

A FinTech startup wants an **AI agent**: software that takes an instruction in plain English, such as *"flag transaction 4471 as suspicious and freeze the card,"* and turns it into exact calls to their internal software. Your job is to:

1. **Teach** an open-source language model to produce those calls reliably (fine-tuning).
2. **Measure** how good it is on a standard benchmark (BFCL).
3. **Make it fast and cheap to run** (optimization), then run it as it would run in production and measure its speed under load.
4. **Present** your choices in 15–20 minutes, and share the code at least 3 days before.

Their ranking is **accuracy first, then latency, then cost**. That order should drive every decision you make. For example, a speed trick that loses accuracy is a bad trade here.

---

## 2. Core concepts

### LLM (Large Language Model)
A neural network trained to predict the next piece of text (a *token*, roughly ¾ of a word). Chat models like Llama or Qwen are LLMs that were further trained to follow instructions.

### Function calling (tool calling)
Instead of answering in prose, the model outputs a structured call. It is given a list of available functions, each described in JSON Schema (name, parameters, types, required fields). Then it outputs something like:

```json
{"name": "freeze_card", "arguments": {"card_id": "8812", "reason": "fraud_suspected"}}
```

The application runs that function and can feed the result back. "Precise" is the key word in the brief. A wrong parameter name or type makes the call fail, and in finance a wrong value is worse than no call at all.

### Fine-tuning
You take a model that has already been trained and train it a bit more on examples of the exact behaviour you want. It's cheap compared with training from scratch, because the model already knows language and only needs to learn the task format and habits.

### ToolACE (training data)
`Team-ACE/ToolACE` on Hugging Face is about 11k synthetic conversations. Each one has a system prompt listing tools, a user request, and the correct function call(s). They were generated by an automated pipeline that covers thousands of APIs. It's standing in for the client's "proprietary dataset." The authors' own **ToolACE-8B** model (Llama-3.1-8B fine-tuned with LoRA) is a published reference point you can compare against.

### BFCL (evaluation)
The **Berkeley Function Calling Leaderboard**, now at v4, in the `gorilla` GitHub repo and installable as `bfcl-eval`. It's the industry-standard test for function calling.

The **"python" subset** means the Python-function test categories:

| Category | What it tests |
|---|---|
| `simple_python` | One function, one call |
| `multiple` | Pick the right function from several |
| `parallel` | Several calls to one function in one turn |
| `parallel_multiple` | Several calls across several functions |
| `live_*` variants | The same, on real user-contributed prompts |

It scores the model's output by parsing it into an **AST** (abstract syntax tree, the structure of the code) and checking function name, parameter names, types and allowed values. It doesn't just compare strings.

### H100
NVIDIA's data-center GPU with **80 GB** of memory. It natively supports **FP8**, an 8-bit number format that roughly halves memory use and speeds up the math compared with the usual 16-bit (**BF16**). You get one of these on Nebius.

### Nebius Token Factory
Nebius's managed inference platform (formerly AI Studio). It serves open models through an **OpenAI-compatible API** and supports post-training (LoRA and full fine-tuning) on Qwen3, Qwen2.5, Llama 3.1/3.2, GPT-OSS and others.

"Deploy as if for Token Factory" means you should pick a base model and output format it can host, and build a serving setup that mirrors theirs: OpenAI-compatible API, standard Hugging Face weights, a tool-call parser.

## 3. Step-by-step plan

### Step 0: Environment (half a day)

- Create the VM **exactly** as specified: H100 SXM, preset *1 GPU / 16 vCPU / 200 GB RAM*, **Regular** (not preemptible), username and SSH key in the Access tab, all other settings default.
- Name it `Name_Surname_dd_YYYY_MM_DD` (demo date).
- Put everything in a Git repo from the start, with pinned versions (`requirements.txt` or `uv.lock`), fixed random seeds, and a `Makefile` or shell scripts. **"Reproducible" is an explicit grading criterion.**

### Step 1: Pick the base model (task 1a)

Things to weigh:

- **Size vs. the GPU.** Around 8B parameters is the sweet spot. It fits on one H100 for training and serves 16–32 concurrent users with low latency. A 70B model won't train on one GPU in any reasonable way.
- **Native tool-calling ability.** You want a model that already has a tool-call format in its chat template.
- **Deployability on Token Factory.** It should be on their supported list.
- **License.** Apache-2.0 is simplest for a commercial FinTech.

The candidates:

| Model | Why |
|---|---|
| **Qwen3-8B** (lead choice) | Strong built-in tool calling, Apache-2.0, supported for LoRA and full fine-tuning on Token Factory, good vLLM parser support |
| Llama-3.1-8B-Instruct | What ToolACE-8B was built on, so you get a direct apples-to-apples comparison with the paper |
| Qwen3-4B / 1.7B | Cheaper and faster; also fits full fine-tuning on one H100 |

**The argument for the presentation:** *"I picked the smallest model that meets the accuracy bar, because latency and cost come next. It's on the client's target platform and its license is commercially safe."*

> **Always measure a baseline first.** Run BFCL on the untuned models before training. Without that "before" number, your fine-tuning gains have nothing to compare against.

### Step 2: Prepare the data

- **Convert ToolACE into the model's chat template.** The chat template is the exact wrapper of special tokens the model expects around system, user, assistant and tool messages. Qwen3, for example, expects `<tool_call>…</tool_call>` blocks. If training uses a different format from the one inference and BFCL use, accuracy falls apart. **This is the most common hidden failure.**
- **Loss masking.** Compute the training loss only on the assistant's answer tokens, not on the system prompt or tool schemas. The model should learn to *produce* calls, not to memorize schemas.
- **Hold out a validation split** (around 5%) so you can watch for **overfitting**, which is when the model memorizes training examples instead of generalizing.
- **Check for contamination.** Make sure no BFCL test items overlap with the training data.
- **Look at lengths.** Tool schemas make prompts long. Set the maximum sequence length (for example 4k–8k tokens) from the real distribution.

### Step 3: Fine-tuning methods to compare (task 1b)

| Method | What it is | Trade-off |
|---|---|---|
| **Full fine-tuning** | Update every weight | Highest ceiling, but an 8B model with the Adam optimizer needs about 16 bytes per parameter (~130 GB). That doesn't fit on 80 GB without tricks, so do it on the 4B model or with 8-bit optimizers and offloading |
| **LoRA** (Low-Rank Adaptation) | Freeze the model and train small add-on matrices (an *adapter*, ~0.1–1% of the parameters) | Fast, fits easily, often within a point or two of full fine-tuning; adapters can be merged in or hot-swapped when serving |
| **QLoRA** | LoRA on top of a 4-bit-compressed frozen model | Least memory, but slower and often slightly less accurate; mainly useful on smaller GPUs |
| **DoRA** (optional) | A LoRA variant that splits weights into magnitude and direction | Sometimes a small accuracy gain for little extra cost |

**Suggested experiment grid** (kept to what one GPU can do in the time):

1. Base model, no training (baseline)
2. LoRA, r = 16
3. LoRA, r = 64
4. QLoRA
5. Full fine-tuning on Qwen3-4B

**r** (rank) is the size of the LoRA matrices: higher means more capacity but more to train. Report BFCL scores for every variant. **That table is the core of your results.**

### Step 4: Training best practices (task 1c)

These are what the brief means by "apply all best practices." Each one is worth naming in the demo:

- **BF16 mixed precision.** Train in 16-bit for speed and memory, with minimal accuracy loss.
- **Learning rate plus warmup and cosine decay.** LoRA typically uses around 1e-4 to 2e-4; full fine-tuning around 1e-5. Warmup ramps the rate up gently at the start, and cosine decay lowers it smoothly toward the end.
- **1–3 epochs** (full passes over the data), with **early stopping** on validation loss.
- **Gradient checkpointing.** Recompute some intermediate values instead of storing them. It saves memory at a small speed cost.
- **FlashAttention and sequence packing.** A faster attention implementation, and bundling several short examples into one sequence so less compute is wasted on padding.
- **Apply LoRA to all linear layers**, not only the attention layers. This usually gives better quality.
- **Fixed seeds and experiment tracking** (Weights & Biases or MLflow) so every run can be compared and reproduced.
- **Evaluate on BFCL, not only on loss.** Lower loss doesn't guarantee better function calls.

**Training framework options:**

| Framework | Notes |
|---|---|
| Hugging Face **TRL + PEFT** | The standard; transparent and well documented |
| **Unsloth** | Often 2× faster with less memory on a single GPU; a good fit here |
| **Axolotl** / **LLaMA-Factory** | Config-file driven; good for reproducibility |

A defensible choice: *"TRL/PEFT, or Unsloth for speed on one GPU. Standard HF format output, so it drops straight into vLLM and Token Factory."*

### Step 5: Optimize for inference (task 2a)

- **Merge the LoRA adapter** into the base weights. That leaves one plain model and removes adapter overhead. Alternatively, keep it as an adapter if Token Factory will serve it as one.
- **Quantization** means storing weights in fewer bits so the model is smaller and faster:
  - **FP8** (W8A8: weights and activations in 8 bits). Native on H100 and usually within about 0.5 points of BF16 accuracy. **The default choice given "accuracy first."**
  - **INT4 AWQ/GPTQ.** Smaller and cheaper, but riskier for exact argument values. Test it, and only adopt it if BFCL holds up.
  - Tool: `llm-compressor` (from the vLLM project) produces formats vLLM loads directly.
- **Re-run BFCL on every optimized variant.** The deliverable is a table of accuracy against speed for BF16, FP8 and INT4.
- **Serving-side settings:**
  - **Prefix caching.** Tool schemas repeat across requests, so their processing can be reused. A big TTFT win.
  - **Chunked prefill.**
  - The right `max-num-seqs`.
  - Optionally **speculative decoding** (a small draft model guesses tokens and the big model checks them).

### Step 6: Deploy as for production (task 2b)

**Hosting framework:** **vLLM** is the natural pick:

- The de facto open-source inference server.
- OpenAI-compatible API, the same interface Token Factory exposes.
- Built-in tool-call parsers (`--enable-auto-tool-choice --tool-call-parser hermes` for Qwen).
- FP8 and LoRA support.
- **Continuous batching**: new requests join the running batch instead of waiting their turn, which is essential for 16–32 concurrent users.

**SGLang** is a strong alternative, and you can mention that you considered it.

**Make it look like production:**

- Docker image, health check, and a pinned model revision
- Metrics endpoint for Prometheus
- Sensible timeouts and maximum lengths
- Optionally, a JSON-schema check on outputs before any API is actually called (a finance-specific safety point worth mentioning)

**Run BFCL against the live endpoint**, not an offline script, so you test exactly what you would ship:

```bash
export LOCAL_SERVER_ENDPOINT=localhost
export LOCAL_SERVER_PORT=8000

bfcl generate --model <your-model> --test-category python --skip-server-setup
bfcl evaluate --model <your-model> --test-category python
```

You may need to register a small **model handler** in BFCL so it knows your model's prompt and tool format. Getting that handler right is often the hardest part of the whole pipeline.

### Step 7: Benchmark performance (task 2c)

**The metrics:**

| Metric | Meaning | Why it matters here |
|---|---|---|
| **TTFT** (time to first token) | Time from sending the request to the first output token | The "is it responding?" feel; with long tool-schema prompts it's usually the dominant cost |
| **TPOT / ITL** (time per output token / inter-token latency) | How fast tokens stream after the first one | Streaming speed |
| **E2E latency** | Total time per request | Function-call outputs are short, so this sits close to TTFT plus a few dozen tokens |
| **Throughput** | Output tokens/s and requests/s across all users | Drives **cost per 1M tokens**, which links back to the cost priority |
| **Percentiles** (p50 / p95 / p99) | Median vs. worst cases | SLAs are written against the tails, so always report them |

**How to run it:**

- Tools: `vllm bench serve`, GuideLLM, or NVIDIA GenAI-Perf.
- Sweep concurrency across **1, 8, 16, 24, 32**.
- Use realistic prompts (real ToolACE/BFCL-style prompts with schemas, roughly 1–2k input tokens and 50–150 output tokens), not random text.
- Run warm-up requests first.
- Compare **BF16 and FP8**, and **with and without prefix caching**.
- Present it as charts of latency against concurrency.

The story should read something like: *"At 32 concurrent users, FP8 gives p95 TTFT of X ms with Y% of BF16 accuracy."*
